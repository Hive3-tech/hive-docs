Use these fields to schedule events from a calendar or another system, set where they happen (an address, a meeting link or a Hive3 3D world), open them for automatic RSVPs or organizer approval, and book a world for them. Events use the shared operations in [Events, courses, content, quests and jobs](/developers/api-resources): list, get, update and archive on `/api/v1/events`, with the same scopes, owner selector, visibility rules, `Idempotency-Key` header and limits (50 event creates per day, 128 KiB per request). To approve RSVPs or record attendance, see [Participation workflows](/developers/api-workflows).

The examples read the key from `HIVE_API_KEY`. Some field names still say `community` or `person`; both identify accounts.

## Event fields

| Field | Type | Notes |
|---|---|---|
| `title` | string | Required. |
| `description` | string | Event text. `shortDescription` defaults to it. |
| `location` | string | `irl` (shown as "In person"), `virtual` or `metaverse`. See [Event types](#event-types). |
| `venue` | object | Where an `irl` event happens. See [Venue](#venue). |
| `meeting` | object | How guests join a `virtual` event. See [Meeting](#meeting). |
| `checkInMode` | string | `self` or `door`, for `irl` events. Default `self`. |
| `eventSlots` | array | One object per session. Empty is allowed; see [Time slots](#time-slots). |
| `autoEnroll` | boolean | Default `false`: RSVPs wait for organizer approval. `true` accepts RSVPs automatically. |
| `worldId` | string | The 3D world to book for a `metaverse` event: a world ID from [`GET /api/v1/worlds`](#list-bookable-worlds), or `default` for the owning account's default world. Leave it out for an event outside any world. See [Book a world](#book-a-world). |
| `maxCapacity` | integer | Attendee limit. For world events it must be a whole number from 1 up to the world's limit. |
| `visibility`, `subscriptionId`, `badges` | | As in [Shared behavior](/developers/api-resources#shared-behavior). |
| `imageUrl`, `heroImage`, `imageStorageId`, `heroImageStorageId` | string | Cover images (`image`, `thumbnailUrl` and `bannerImageUrl` also work). |

The server owns `metaverseTime`, `courseId`, `kind`, `officeHours` and `sessionKey`; values you send for them are ignored. Course office-hour sessions cannot be updated here (`400 invalid_request`, `Course office hours are edited from their course`).

## Create an event

<Endpoint method="POST" path="/api/v1/events" scopes={["resources:write", "communities:write (community owner)"]}>

## Event types

`location` sets the event type. Every event read returns `location`, `venue`, `meeting` and `checkInMode` (`null` when they don't apply; `checkInMode` is `null` unless `location` is `irl`).

| `location` | Needs | Guests see |
|---|---|---|
| `irl` | `venue`, optional `checkInMode` | The address, a map and directions on the event page. Attendance is recorded by QR check-in at the venue, which is set up in the app. |
| `virtual` | `meeting` | The meeting app. Through the API the full `meeting` goes only to keys for the owning account (or that manage it); other readers get the provider. In the app, approved guests see the link. See [Meeting](#meeting). |
| `metaverse` | `worldId` | The world, entered from the event page. |

When you leave `location` out, it is worked out from the request: `metaverse` with a `worldId`, `virtual` with a `meeting`, `irl` with a `venue`. On `PATCH` the stored type, venue, meeting and check-in mode are kept for fields you omit. On create with none of these, an event whose slot links point at a known meeting service (Zoom, Google Meet, Teams and similar) becomes `virtual` with that link as its `meeting`; anything else becomes `irl`.

The API does not require a `venue` for `irl` events, so you can add the address later; the app's event form does. Changing `location` clears fields that belong to the old type, for example the `meeting` when a virtual event becomes `irl`.

### Venue

| Field | Type | Notes |
|---|---|---|
| `address` | string | Required in a `venue`, at most 300 characters. Public: everyone who can see the event sees it. |
| `name` | string | Venue name, at most 120 characters. |
| `instructions` | string | "Getting there" notes such as parking or a door code, at most 1,000 characters. |
| `city` | string | At most 120 characters. Shown on event cards as "In person · city". |
| `placeId` | string | A Google Maps place ID, at most 300 characters. Improves the map and directions. |
| `latitude`, `longitude` | number | Kept only when both are sent and in range. |

### Meeting

| Field | Type | Notes |
|---|---|---|
| `url` | string | Required. An `https://` link, at most 2,048 characters. A link without a scheme gets `https://`. |
| `provider` | string | `zoom`, `google_meet`, `microsoft_teams`, `x_spaces`, `discord`, `youtube` or `other`. When omitted, it is recognised from `url` (`other` when unknown). |
| `instructions` | string | Joining details such as a passcode or dial-in number, at most 1,000 characters. |

The join link is private. Through the API, only keys for the owning account (or a key that manages it) read the full `meeting`; any other reader gets only the provider, for example `"meeting": { "provider": "zoom" }`. In the app, the link is shown to the event's hosts and moderators and to guests whose RSVP is approved and who still have access (ticket, subscription or membership), and approved guests also get it in their confirmation email. For ticketed or members-only events, the link counts as protected content, just like the description.

```bash
curl -X POST https://app.hive3.tech/api/v1/events \
  -H "Authorization: Bearer $HIVE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"title":"Office Hours","location":"virtual","meeting":{"url":"https://us02web.zoom.us/j/123456","instructions":"Passcode 4242"},"autoEnroll":true,"eventSlots":[{"startsAt":"2030-01-20T17:00:00Z","endsAt":"2030-01-20T18:00:00Z"}]}'
```


### Filter the list by type

`GET /api/v1/events?location=virtual` lists only events of that type (`irl`, `virtual` or `metaverse`); any other value returns `400 invalid_request` (`location must be irl, virtual or metaverse`). A filtered page can hold fewer than `limit` events while `page.hasMore` is still `true`; keep following `nextCursor`.

### Event type errors

Each returns `400 invalid_request` and changes nothing:

| Message | When |
|---|---|
| `location must be irl, virtual or metaverse` | Another `location` value. |
| `Metaverse events need a world.` | `location: "metaverse"` without a `worldId` on the event. |
| `Only metaverse events can book a world.` | A `worldId` with `location` `irl` or `virtual`. |
| `Virtual events need a meeting link that starts with https://.` | A `virtual` event without a `meeting`, or with a link that isn't `https`. |
| `meeting.provider must be zoom, google_meet, microsoft_teams, x_spaces, discord, youtube or other` | An unknown `provider`. |
| `checkInMode must be self or door` | Another `checkInMode` value. |
| `address must be 300 characters or fewer` | A venue or meeting field over its limit (the message names the field and its limit). |

Check-in itself (event QR codes, passes and the door scanner) and Google Calendar sync are only in the app. See [Check in at events](/create/check-in-at-events).

## Time slots

Each slot is an object with required `startsAt` and `endsAt` and optional `name` (or `title`), `image` and `links`. Both timestamps must be ISO 8601 with `Z` or an explicit offset, and `endsAt` must be later than `startsAt`:

```text
2030-01-01T10:00:00.000Z
2030-01-01T12:00:00+02:00
```

A timestamp without an offset is rejected rather than guessed from a separate timezone. An invalid slot returns `400 invalid_request` and names the slot, for example `Event slot 1: startsAt and endsAt must be ISO 8601 timestamps with a timezone offset (for example 2030-01-01T10:00:00.000Z)` or `Event slot 1: endsAt must be after startsAt`. An empty `eventSlots` array is allowed. On `PATCH`, slots are validated only when you send `eventSlots`, and the array you send replaces the stored one.

## Events that have started

An event has started when its earliest valid slot start is at or before the current time, including after it ends. From then on `PATCH` returns `409 conflict` (`This event has started and can no longer be edited.`) and `DELETE` returns `409 conflict` (`This event has started and can no longer be cancelled.`). Events without a valid start remain editable and cancellable. Updating an archived event returns `404`.

## Book a world

Send `worldId` to book a 3D world for the event. Without `worldId` the event is not in a world and spends no metaverse time. When the user names a venue (for example "the Dome" or "our own world"), look up its ID with [`GET /api/v1/worlds`](#list-bookable-worlds) and send that ID rather than `default`. The owning account's plan decides which worlds it can book:

| Plan | Worlds |
|---|---|
| Honey Bee | Any shared world (today Hive3 Dome and Night Lounge). |
| Swarm | The shared world chosen as the account's default on the dashboard. The app offers only that one; the API also accepts another shared world's ID. |
| Royal Hive | Only the account's own world. |
| Worker Bee | None. |

Other combinations return `400` with the reason (`Booking a shared world needs a Honey Bee or Swarm plan.`, `Only this world's Royal Hive can book it.`, `This account books its own world.`, `That world isn't available.`).

### List bookable worlds

<Endpoint method="GET" path="/api/v1/worlds" scopes={["resources:read", "communities:read (another account)"]}>

Lists the worlds the owning account's events may book, as the app's event form offers them: every shared world for Honey Bee, only the default shared world for Swarm, only its own world for Royal Hive, and none for Worker Bee. A world that is not listed can't be booked for that account, so tell the user instead of booking a different one.

| Name | In | Type | Required | Notes |
| --- | --- | --- | --- | --- |
| `account` | query | string | No | Account ID or `@handle`. Defaults to the key owner. |

For another account the key also needs `communities:read`, must include that account when the key is limited to selected accounts, and the key owner must currently be an owner, admin or moderator of it. See [managed accounts](/developers/api-authentication#managed-accounts).

```bash
curl "https://app.hive3.tech/api/v1/worlds?account=@design-guild" \
  -H "Authorization: Bearer $HIVE_API_KEY"
```

Returns `200`. `kind` is `shared` (a Hive3 venue) or `dedicated` (the account's own world). When worlds are listed, exactly one has `isDefault: true`: the one `"worldId": "default"` books. `needsDedicatedSetup: true`, with an empty list, means a Royal Hive account must choose its world's design on the dashboard first. The response has no admission settings, hosts or other accounts' data.

```json
{
  "data": {
    "worlds": [
      { "id": "world_123", "name": "Hive3 Dome", "kind": "shared", "isDefault": true },
      { "id": "world_456", "name": "Night Lounge", "kind": "shared", "isDefault": false }
    ],
    "needsDedicatedSetup": false
  }
}
```

Errors: `403 insufficient_scope` (missing `resources:read`, or `communities:read` for another account), `403 forbidden` (the key does not include the account, or your role does not allow it), `404 not_found` (account not found).

</Endpoint>

### The default world

Send `"worldId": "default"` to book the owning account's default world without looking up a world ID: the world [`GET /api/v1/worlds`](#list-bookable-worlds) lists with `isDefault: true`. Use it only when the user wants a world event but names no venue. It works on create and on `PATCH`, and with the [CLI](/developers/cli-commands-resources) as `--world default` (0.5+).

- **Swarm:** the shared world chosen as the account's default on the dashboard, the same one the app's event form books.
- **Honey Bee:** the account's default shared world, which is Hive3 Dome unless another shared world is stored as its default. (In the app, Honey Bee picks a world for each event.) For Swarm and Honey Bee alike, a default world that is no longer available falls back to the first shared world (Hive3 Dome).
- **Royal Hive:** the account's own world. Before its design is chosen the request returns `400` (`This account's own world isn't set up yet. Choose its design on the dashboard first.`).
- **Worker Bee:** `400` (`This account has no world to book. Worlds come with a paid plan.`).

Once `default` is resolved, the rules below apply exactly as for an explicit `worldId`. A `400` or `409` creates or changes nothing.

### Booking rules

- **One slot.** A world event has exactly one slot (`World events have exactly one time slot.`).
- **Attendee limit.** `maxCapacity` is a whole number from 1 to 500 in a shared world or from 1 to 100 in a Royal Hive's own world. It defaults to that maximum.
- **No overlaps.** A slot that overlaps another booking on the same world returns `409 conflict` (`That time is already booked in this world (…)`). Back-to-back bookings are allowed.
- **Metaverse time.** An event in a shared world spends the owning account's metaverse time. Creating it charges its duration in minutes (Swarm includes 60 minutes per UTC calendar month), a `PATCH` refunds the previous charge and charges the new one, and archiving an event that has not started refunds it. When time runs out the request returns `400` (`You're running out of metaverse time. Shorten the event or top up your balance.`) and nothing changes. Events in a Royal Hive's own world are free.
- **Moving worlds.** `PATCH` with a different `worldId` removes the metaverse join links in the slots that pointed into the previous world.
- **Moving out of a world.** `PATCH` with `location` set to `irl` or `virtual` (and the `venue` or `meeting` it needs) takes the event out of its world: the booking and the old world's join links are removed, and metaverse time it used in a shared world is refunded like any other `PATCH`. Sending `worldId` together with `irl` or `virtual` returns `400` (`Only metaverse events can book a world.`). Without `location`, a `PATCH` keeps the event's world.

```bash
curl -X PATCH https://app.hive3.tech/api/v1/events/event_123 \
  -H "Authorization: Bearer $HIVE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"location":"virtual","meeting":{"url":"https://meet.google.com/abc-defg-hij"}}'
```

```bash
curl -X POST https://app.hive3.tech/api/v1/events \
  -H "Authorization: Bearer $HIVE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"title":"Town Hall","location":"metaverse","worldId":"default","maxCapacity":100,"eventSlots":[{"startsAt":"2030-02-01T17:00:00Z","endsAt":"2030-02-01T18:00:00Z"}]}'
```

## Reschedule an event

<Endpoint method="PATCH" path="/api/v1/events/{id}" scopes={["resources:write", "communities:write (community-owned)"]}>

Replaces the slots of an event that has not started. Fields you omit keep their value.

```bash
curl -X PATCH https://app.hive3.tech/api/v1/events/event_123 \
  -H "Authorization: Bearer $HIVE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"eventSlots":[{"name":"Session","startsAt":"2030-01-16T17:00:00.000Z","endsAt":"2030-01-16T18:00:00.000Z"}]}'
```

Returns `200` with the updated event. Errors: `400` (invalid slot, world rule, [event type](#event-types) error), `404 not_found`, `409 conflict` (the event has started, or the new slot overlaps another booking).

Guests are kept informed whichever way you edit: when the time, venue, check-in mode, join link or world changes, approved guests get one "Updated details" email (edits a few minutes apart are combined), and archiving an upcoming event emails everyone who RSVP'd and was not declined.

</Endpoint>
